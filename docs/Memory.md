## Original Planning Snapshot (Phase 0 — kept for history)
- Target users: approximately 320 college students
- Student quota: 1 GB aggregate per top-level student folder
- Planned student storage: 320 GB; available Google Drive storage: 400
  GB; buffer: ~80 GB
- No traditional login; public folder browsing; optional folder
  password; no per-file artificial size limit
- Frontend hosting target: GitHub Pages; file storage target: owner's
  Google Drive via the Drive API

## Product Decisions
0. Backend/database: Cloudflare Workers (Hono framework) + Cloudflare D1, chosen for free-tier fit and easy server-side secret handling.
1. Everyone can browse public folders.
2. A folder can optionally be password-protected.
3. Folder creators receive a secret management credential/link.
4. Google Drive credentials stay server-side.
5. Quota is checked server-side.
6. Security is a priority despite the zero-cost goal.
7. ECSHub is the visual inspiration.
8. File upload permissions: public folders — anyone can upload. Protected folders — only the management-token holder (owner) can upload. Viewing/downloading files uses the same access rule as opening the folder (open for public, unlock token or management token for protected). Deleting a file always requires the management token, regardless of the folder's public/protected status.
9. Frontend wired to the real backend starting Phase 8 (rather than staying mock) — the phase's loading/error/upload-progress requirements needed real latency and real failures to be meaningful.

## Decisions Still To Confirm
- Whether subfolders count toward the same 1 GB quota (moot until subfolders are actually implemented — they aren't yet).
- Admin dashboard requirements (no dedicated dashboard exists; `security_events` is queryable directly via `wrangler d1 execute`, and `docs/Operations.md` documents the manual procedures that stand in for one today).
- File preview behavior (not implemented — files are download-only).

## Resolved (were previously "Still To Confirm")
- Recovery procedure if a management token is lost: **resolved as "no self-serve recovery, by design"** — a recoverable token would defeat its purpose. `docs/Operations.md` documents the admin-assisted manual procedure for when identity can be verified out-of-band.
- **Newly surfaced gap, not yet resolved**: there's currently no way for a folder owner to change their password *after* creation (only set one at creation time). `docs/Operations.md` has a manual admin-assisted workaround; a real `PATCH`-password endpoint would be the proper fix if this comes up often enough to justify it.

### Phase 3 — Folder System (in progress)
- Google Drive auth model chosen: the owner authorizes the app once via OAuth (not a service account, since service accounts have their own separate, mostly-empty Drive storage — files need to live in the owner's actual Drive). Refresh token + client id/secret stored as Worker secrets; see `backend/README.md` > "Google Drive setup" for the one-time OAuth Playground steps.
- Added `src/drive.js` (create/rename/trash Drive folders), `src/crypto.js` (SHA-256 hashing, timing-safe compare, token/id generation — all via native Web Crypto, no new dependency), `src/validate.js` (folder name validation: letters/digits/spaces/basic punctuation, 1–80 chars, no path characters), `src/auth.js` (management-token verification), `src/routes/folders.js`.
- New endpoints: `POST /api/folders` (creates the Drive folder first, then the DB row; trashes the Drive folder if the DB write then fails, so nothing orphans), `GET /api/folders` (list, public fields only), `GET /api/folders/:id`, `PATCH /api/folders/:id` (rename, management token required), `DELETE /api/folders/:id` (trashes the Drive folder + soft-deletes the DB row, management token required).
- Management token: 32 random bytes, shown to the client exactly once at creation, only its SHA-256 hash is ever stored. Verified via `Authorization: Bearer <token>` and a constant-time comparison.
- Folder listing never selects `password_hash` or `management_token_hash` — only a dedicated internal query (`getFolderWithSecrets`, used solely by the auth check) can see them.
- Password protection deliberately deferred to Phase 4 (matches Phases.md's split): every folder is currently unprotected; `password_hash` stays NULL until then.
- Not yet done: no password/unlock flow, no rate limiting, no file routes (Phase 5), backend still not deployed — `POST/PATCH/DELETE /api/folders` are untested against the real Google Drive API in this environment (no network access here) and should be smoke-tested locally.

### Phase 4 — Password Protection (in progress)
- **Deviated from the plan noted at the end of Phase 3**: passwords use PBKDF2-SHA256 (native Web Crypto), not Argon2id/bcrypt via `hash-wasm`. Reason found through local benchmarking: Cloudflare Workers' free plan caps CPU time at ~10ms/request; a full Argon2id run in pure JS/WASM measured well over that on its own. PBKDF2 via `crypto.subtle` is hardware-backed and fits. Its iteration count (30,000, vs. OWASP's 210,000+ recommendation) is also reduced for the same CPU-budget reason — full reasoning and benchmark numbers are in `src/password.js`'s header comment. This is a real security/free-tier trade-off, made deliberately, worth revisiting if the project ever moves off the Workers free plan (the iteration count is stored inside each hash string, so raising it later doesn't invalidate existing passwords).
- Added `src/password.js` (hash/verify), `src/rateLimit.js` (unlock-attempt rate limiting: 5 attempts per 15 minutes per folder+IP, using the `rate_limits` table from Phase 2), `src/session.js` (stateless, HMAC-signed temporary unlock tokens — no session table needed).
- `POST /api/folders` now accepts an optional `password` field (4–100 chars); hashed before storage, `password_hash` stays NULL for unprotected folders as before.
- New `POST /api/folders/:id/unlock` — rate-limited first (so a locked-out attacker never even reaches the password check), then verifies the password, then on success clears that IP's rate-limit history and returns a 30-minute unlock token. Phase 5's file routes are expected to accept this token in place of a password for protected folders.
- New secret: `UNLOCK_SESSION_SECRET` (any long random string, signs the unlock tokens).
- Verified locally (this environment has no network, but password hashing/verification and unlock-token issuing/verifying are pure computation, so they were run and round-tripped successfully — see the Phase 4 chat for the exact commands run).
- Not yet done: file routes to actually consume the unlock token (Phase 5), no admin visibility into rate-limit table growth/cleanup (old windows accumulate — noted as a future cleanup task, not urgent at this scale), backend still not deployed anywhere.

### Phase 5 — File Upload/Download (in progress)
- Upload permission decision (was open, now resolved — see Product Decisions #8): public folders let anyone upload; protected folders restrict uploads to the management-token holder. Viewing/downloading follows the same rule as opening the folder; deleting is always owner-only.
- `POST /api/folders/:id/files` (multipart/form-data, field `file`): checks quota *before* touching Drive — sums the folder's active files (`getFolderUsedBytes`, a live query, not a cached counter, so it can't drift) and rejects with `quota_exceeded` if the new file would push it past 1 GB. Uploads via a single multipart/related request to Drive (metadata + bytes together) rather than uploadType=media plus a follow-up PATCH — one round trip. If the DB insert fails after a successful Drive upload, the orphaned Drive file is trashed, mirroring the folder-creation rollback pattern from Phase 3.
- `GET /api/folders/:id/files` — lists a folder's files, gated by the same `assertFolderViewAccess` helper files.js uses for downloads.
- `GET /api/files/:id` — streams bytes from Drive through the Worker (`response.body` piped straight into the returned `Response`, no buffering) rather than ever exposing a Drive link or credential to the client. This is also what keeps protected-folder files actually protected — a public Drive link would bypass the password entirely.
- `DELETE /api/files/:id` — always requires the folder's management token, even for public folders, since deletion is destructive.
- `PATCH /api/files/:id` — rename, also management-token only. Reuses `renameDriveFolder` since Drive's rename call works identically on files and folders (no separate Drive helper needed).
- Refactored `auth.js`: extracted `assertManagementToken` (the Bearer-token check, now shared by folder rename/delete and file upload/delete) and added `assertFolderViewAccess` (view rule: public folders open, protected folders need `Authorization: Unlock <token>` — verified via `session.js`'s `verifyUnlockToken` — or the management token).
- No schema changes needed — the `files` table from Phase 2 already had everything (`folder_id`, `drive_file_id`, `original_name`, `mime_type`, `size_bytes`, `status`).
- Verified locally: the exact multipart/related body construction `uploadDriveFile` sends to Drive was built and inspected byte-for-byte in this environment (no network here to hit the real Drive API, but the body format itself was confirmed correct) — see the Phase 5 chat for the command.
- Not yet done: no admin dashboard, no file preview, no subfolder support, backend still not deployed or tested against the real Google Drive API end-to-end.

### Phase 6 — Quota (in progress)
- Closed a real race condition: the old upload flow checked "is there room?" and then inserted the file row as two separate steps, so two uploads landing at nearly the same moment could both pass the check before either had written, together pushing a folder over 1 GB. Fixed with `insertFileIfWithinQuota` in `db.js` — the quota check and the insert are now one atomic SQL statement (`INSERT ... SELECT ... WHERE <quota holds>`), which SQLite (D1's engine) executes as a single atomic unit, so no concurrent write can land inside that window. Verified locally with Node's built-in SQLite: inserts up to exactly the quota boundary succeed, the next byte over is rejected, final total never exceeds the limit (see backend/README.md > "Concurrent uploads" for the numbers).
- The upload route keeps its old pre-check too (cheap, avoids wasting a Drive upload on an obviously-oversized file) but that's now explicitly documented as *not* the real enforcement — the atomic insert is. If a upload loses the race, its already-uploaded Drive file is trashed, same cleanup pattern used elsewhere.
- `GET /api/folders` and `GET /api/folders/:id` now also return `quotaBytes` (1 GB, currently a constant) and `remainingBytes`, so a usage meter never has to hardcode the limit.
- Scope decision: didn't touch the frontend in this phase — it's still deliberately mock/backend-free (consistent with every phase so far), and Phases.md's "show usage meter" is read here as "the API makes a usage meter trivial to build," which it now does. Actually wiring the frontend to the real API isn't explicitly its own phase in Phases.md — worth flagging to the user before assuming when that happens.
- Not yet done: no stress test against a real concurrent-request scenario over the network (the atomicity proof is against the SQL engine directly, which is the part that actually matters, but an end-to-end test would still be reassuring), backend still not deployed.

### Phase 7 — Security Hardening (in progress)
- Security headers: Hono's built-in `secureHeaders()` middleware (not hand-rolled — already a dependency, well-tested), with `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'` (this API never serves HTML), and `Cross-Origin-Resource-Policy: cross-origin` (the default `same-origin` would fight the whole point of a frontend on a different origin calling this API).
- CORS: `ALLOWED_ORIGIN` (singular) → `ALLOWED_ORIGINS` (comma-separated list) in `wrangler.toml`, so local dev and the production frontend origin can coexist without code changes; methods/headers now explicitly allowlisted instead of left open.
- Added a JSON body-size guard (20 KB cap, checked via `Content-Length` before parsing) — every JSON endpoint here is naturally tiny, so this mainly protects CPU budget from a deliberately oversized body; doesn't touch multipart uploads.
- Hardened `validate.js`: non-string JSON fields (a number/array/object where a name or password was expected) now fail cleanly as 400s instead of throwing an uncaught `TypeError` that the global handler would sanitize into a generic 500. Same fix applied to the unlock endpoint's password field in `folders.js` (`typeof body.password === "string"` check).
- Rate limiting generalized: `rateLimit.js`'s `enforceRateLimit` is now a reusable primitive; unlock attempts (5/15 min/folder+IP, from Phase 4) plus two new limits — folder creation (10/hour/IP) and file uploads (60/hour/IP) — all share it and the same `rate_limits` table.
- Token rotation: `POST /api/folders/:id/rotate-token` (management token required) overwrites `management_token_hash`, invalidating the old token immediately. Unlock tokens (stateless/HMAC-signed, Phase 4) don't get individual revocation by design; noted that rotating `UNLOCK_SESSION_SECRET` is the coarse fallback if that's ever needed (invalidates *all* outstanding unlock tokens at once).
- Audit/security events: new `security_events` table (schema.sql, `CREATE TABLE IF NOT EXISTS` so existing deployments just need to re-run the migration) + `src/audit.js`'s `logSecurityEvent` — append-only, never read back by the API itself. Logs: every rate-limit hit (generic, from inside `enforceRateLimit`), failed management-token checks (`auth.js`), denied protected-folder views, unlock success/failure, and folder/file create/rename/delete/upload/quota-reject/rotate events. A logging failure never blocks the request that triggered it (wrapped, console.error'd, swallowed).
- Error sanitization: reviewed against Phase 2's `AppError`/global-handler setup — found nothing that needed changing, it was already sound.
- Verified: full backend syntax-checked again after all changes; also wrote a small script that statically cross-checks every `import { x } from "./y.js"` against y.js's actual exports across the whole `src/` tree, to catch typos node's syntax check alone wouldn't (no `node_modules` in this environment to do a real module-resolution import test, since there's no network access to `npm install`).
- Not yet done: security headers/CORS/rate limits are unverified against a real deployed Worker (this environment can't reach the network); no automated tests yet (Phase 9); the distributed-brute-force gap noted in Phase 4 (unlock rate limit is per-IP, so many IPs could still combine to guess a password) is still open — flagged, not fixed, since Phases.md doesn't call for it explicitly and it's a harder problem (CAPTCHA or similar) that would need its own product decision.

### Phase 8 — UI Polish (in progress)
- User's call (was open at end of Phase 7): wired the frontend to the real backend now, not later — this phase's "loading/error states" and "upload progress" items need real latency and real failures to be meaningful, so mock data wouldn't have exercised them properly.
- New `js/api.js`: fetch wrapper for every backend endpoint. Upload uses `XMLHttpRequest` specifically (not `fetch`) because `fetch` has no upload-progress event — `xhr.upload.onprogress` is what makes the progress bar real. Download uses `fetch` + blob + a synthetic `<a download>` click rather than a plain link, because a protected folder's download needs an `Authorization` header, which a plain `<a href>` can't send.
- `index.html` restructured into two views toggled by hash-based routing (`#` = dashboard, `#/folder/:id` = detail) — a real router, not query params, so folder links are shareable and the back button works. No page reload between them.
- Auth token storage, deliberately split by lifetime: management tokens (prove folder ownership) go in `localStorage` so they survive across visits on the same device; unlock tokens (prove a protected folder's password was entered) go in `sessionStorage`, matching their 30-minute server-side expiry from Phase 4.
- Folder creation and token rotation both use one shared "token reveal" modal (copy-to-clipboard, "won't be shown again" warning) instead of the old toast — a toast auto-dismissing in ~4 seconds was a bad way to show something the user has exactly one chance to copy.
- An owner who lost their stored token (different device, cleared storage) can paste it back in via a "manage this folder" panel — validated by actually using it for a real request (the file list fetch) rather than trusting it blindly, so a wrong token is caught immediately with a clear error instead of failing confusingly on the next action.
- Deliberate scope trade-off: file rename/delete confirmation uses native `window.prompt`/`window.confirm` rather than custom modals. These are lower-stakes, secondary actions (folder create/delete already have full custom modals), and native dialogs are inherently keyboard/screen-reader accessible via the OS, just not visually styled — a reasonable place to stop given the phase's scope.
- Loading/error states: skeleton placeholders (shimmer) for the folder grid and folder detail while fetching; a dedicated error banner with a "Try again" button if the backend is unreachable (a real, expected case — e.g. if the backend isn't running while the frontend is being previewed) rather than a silently empty page.
- Accessibility pass: skip-to-content link, a real focus-trap + Escape-to-close + return-focus implementation shared by every modal (was ad hoc before), `role="alert"`/`aria-live` on every error/status surface, minimum 40px touch targets for secondary actions on mobile, and the folder cards changed from `<button>` to `<a href="#/folder/:id">` so they're real navigable links (right-click "open in new tab" now works).
- Verified: full syntax check on all JS; a static script cross-checking every `document.getElementById(...)` call in `app.js` against actual `id` attributes in `index.html` (came back clean — this is exactly the kind of typo that's invisible until you click the button in a browser); duplicate-ID check and rough tag-balance check on `index.html`; CSS brace-balance check; all files served correctly over a local static server. Caught and fixed one real bug this way: an initial-load double-fetch of `GET /api/folders` (both an unconditional call and the router doing it again).
- Not yet done: no real browser testing (this environment has no browser, only static/structural checks — genuinely exercising the click-through flows, drag-and-drop, focus trap, and clipboard behavior needs a human or Phase 9's automated tests), no visual QA against the ECSHub-inspired direction beyond reusing Phase 1's established tokens/components, backend still not deployed so the "unreachable backend" error state is the only one exercised so far.

### Phase 9 — Automated Tests (in progress)
- Chose Node's built-in `node:test` over installing Vitest: everything this codebase's logic actually uses (Web Crypto, `fetch`, D1's prepare/bind/run interface) already runs identically in plain Node, so `node:test` tests the real production code with zero new dependencies. Documented Cloudflare's own recommended path (Vitest + `@cloudflare/vitest-pool-workers`, for testing against the actual Workers runtime) as a reasonable future upgrade in `backend/README.md`, not dismissed — just not needed yet.
- Built `test/helpers/fakeD1.js`: a small D1-shaped adapter over `node:sqlite` (same engine D1 runs on) implementing only the `.prepare().bind().run()/.first()/.all()` surface `db.js` actually calls. This lets `db.test.js` import and run the *real* `src/db.js` functions against a real in-memory database, rather than testing a reimplementation of the SQL logic.
- Built `test/helpers/fakeDrive.js`: canned `fetch` responses for the OAuth token endpoint and Drive's folder/file create/rename/trash/download calls, so `routes.test.js` never touches the real network.
- Found and fixed two real bugs purely from writing tests (not from a separate audit pass):
  1. `FOLDER_NAME_PATTERN` in `validate.js` rejected em-dashes — meaning the exact example name in the create-folder form's own placeholder ("Priya — Semester 4 Notes") would have been rejected by real validation if a user typed or pasted it literally. Fixed by adding `\u2013`/`\u2014` to the allowed character set.
  2. The first version of `fakeD1.js` only implemented `.bind().run()/.first()/.all()`, but real D1 (and therefore `db.js`) also calls `.run()/.first()/.all()` directly on a parameterless statement (`listActiveFolders`) — caught immediately as a test failure, fixed by adding those methods to the adapter.
- `db.test.js` includes a direct regression test for the Phase 6 quota race condition: fires two uploads at the same folder concurrently via `Promise.all` against the real `insertFileIfWithinQuota`, asserts exactly one wins when together they'd exceed quota, and asserts final usage never exceeds it.
- **What was actually run vs. not, honestly**: the unit tests (`crypto`, `password`, `validate`, `session`) and `db.test.js` — 45 tests total — need nothing but Node itself and were run directly in this environment; all 45 pass. `routes.test.js` (the Hono-app integration suite, ~20 tests) needs `hono` installed via `npm install`, and this environment has no network access to do that, so it is syntax-checked and written against Hono's documented `app.request(path, init, env)` testing API (verified via a web search of Hono's own docs, including the exact multipart-FormData test pattern) but was **not** executed here. This is flagged plainly in `backend/README.md`'s testing section rather than left implicit — running `npm test` locally after `npm install` is the real verification step, not something to take on faith from this log.
- Not yet done: `routes.test.js` unverified by actual execution (see above); no frontend test suite (Phase 8's UI still only has the earlier static/structural checks, no real browser-based tests); no CI configuration to run these automatically on push.

### Phase 10 — Deployment (in progress)
- **What was actually possible to do here vs. not**: deployment requires a Cloudflare account, a GitHub repo the owner controls, and real Google OAuth credentials -- none of which this environment has access to (no network to Cloudflare/GitHub, no credentials). Nothing was actually deployed. What's delivered instead: everything that *can* be prepared in advance -- automation, docs, and a smoke-test script -- so the owner's actual deploy is a short checklist, not a from-scratch research project.

- Verified: both new workflow YAML files parse as valid YAML (the `on:` key showing as Python boolean `True` in that check is a well-known PyYAML 1.1 quirk, not an actual problem -- GitHub's own parser reads it correctly).
- Not yet done (all requiring the owner's actual accounts/credentials, not fixable by more prep): the backend has never been deployed to a real Worker; the frontend has never been published to Pages; `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` repo secrets aren't set; production `ALLOWED_ORIGINS`/`GOOGLE_ROOT_FOLDER_ID`/`window.ECS_DRIVE_API_BASE` still hold placeholder/localhost values; the smoke-test script and `routes.test.js` have never run against anything real.

4. **"Drive shouldn't be public, permissions propagate to children"** — the general Drive-API concern is real, but doesn't apply to this design: the app never calls Drive's `permissions.create` on anything, so there's no sharing to propagate. 5. **"No artificial file-size limit, resumable uploads"** — **was a genuine, real gap; fixed in Phase 12 below.** The old `uploadDriveFile`/upload route buffered the entire file into Worker memory (`file.arrayBuffer()`) and sent it as one multipart request. Replaced with Google Drive's resumable upload protocol, chunked through the Worker — see Phase 12's entry for the full design and audit.

Also asked, not yet answered: whether the project owner's 400 GB is a personal Google One plan or a Google Workspace/Shared Drive setup. The OAuth-as-a-user architecture (not a service account) works with either, but the exact answer affects which OAuth consent-screen "user type" to configure and whether Shared Drives are even an option — needs the owner's confirmation, not something knowable from the codebase alone.

## Phase 12 — Production-Readiness Audit: Resumable Uploads

Triggered directly by the review above's point 5. Scope, per the explicit instruction: fix the upload architecture while preserving the 1 GB aggregate quota and the "no artificial per-file limit" requirement, without exposing Google credentials to the frontend, plus re-verify CORS, authentication, password hashing, management-token security, rate limiting, quota race conditions, and Drive/API failure cleanup.

**Core decision**: replaced the single-request buffered upload with Google Drive's resumable upload protocol, chunked (8 MiB per chunk — a multiple of Drive's required 256 KiB) and proxied through the Worker for every chunk, rather than having the browser send chunks directly to Google's session URI. The direct-to-Google alternative was seriously considered — it avoids proxying bytes through the Worker at all — but rejected: Google's docs for the near-identical Cloud Storage resumable protocol warn a session URI "can be used by anyone... without any further authentication," and Drive's own behavior on that specific point wasn't confirmed precisely enough to hand a live session URI to a browser, given the explicit instruction not to expose Drive credentials to the frontend. Proxying keeps every existing authorization/quota/rate-limit check exactly where it already lived, at the cost of one extra network hop per chunk.

**Why this is required, not optional**: verified via search that Workers' free plan rejects any single request body over 100 MB *before the Worker even runs* (an edge-level rejection, not something in-Worker streaming code can bypass) and caps Worker memory at 128 MB. A single ~150 MB+ file would have hard-failed under the old implementation.

**API**: `POST /api/folders/:id/uploads` (start — same public/protected auth rule as before, checked once at start, not per chunk) returns `{uploadId, chunkSize}`. `PUT /api/folders/:id/uploads/:uploadId` sends one chunk (`Content-Range: bytes <start>-<end>/<total>`) or checks status after a drop (`Content-Range: bytes */<total>`, empty body) — always responds `200`/`201` JSON, **deliberately never Drive's raw `308 Resume Incomplete`**, since a literal 308 would make a browser's `fetch()` try to follow it as an actual redirect instead of reading the response (caught during design, not after shipping). `DELETE .../:uploadId` cancels. Possessing `uploadId` (an unguessable UUID, only ever handed to whoever passed the real auth check at start) is what authorizes each chunk — the same capability-token trust model already used for unlock/management tokens, not re-verified per chunk.

**Quota correctness re-verified, not just assumed carried over**: the completing chunk's quota check uses Drive's own authoritative reported file size — not the client's original declared size, not the server's own running byte tally — closing a possible "declare small, send more" loophole. Goes through the same atomic `insertFileIfWithinQuota` from Phase 6 unchanged, so the same race protection applies; confirmed by re-reading that code path rather than assuming.

**A real bug found and fixed as part of this same audit**: Hono's CORS `allowHeaders` didn't include `Content-Range`, which chunk-upload requests need to send cross-origin — without this, every chunk PUT would fail CORS preflight in a real browser. Fixed, with a regression test.

**Audit findings on the other requested areas** (re-checked, not re-asserted):
- Management-token security: sound, unchanged. The new `uploadId` capability token has 122 bits of entropy (UUID v4), judged sufficient for a short-lived, single-purpose token.
- Password hashing: unchanged from Phase 4; no new issues found.
- Rate limiting: deliberately did **not** rate-limit individual chunk PUTs, only the initiating call (same as before) — limiting every chunk would treat one legitimate large file's ~100+ chunks as 100+ separate upload attempts, the wrong unit to limit.
- Drive/API failure cleanup: a chunk that fails mid-transfer does **not** mark the session aborted (left active so the client can retry/resume) — only explicit cancellation, successful completion, or TTL-based reclaim change status. Confirmed intentional — resumability is the whole point.

**Test coverage added**: `test/drive.test.js` (new) tests the actual resumable-upload client logic with **zero Hono dependency** — `drive.js` never imports Hono, so unlike `routes.test.js`, this file could actually be *run*, not just syntax-checked, in this environment: 5/5 pass. `db.test.js` gained 3 passing tests for the `upload_sessions` table functions. `routes.test.js` gained 5 new tests (multi-chunk, resume-after-drop, cancellation, quota rejection at the true boundary, the CORS regression) — written against Hono's documented API but still unexecuted here, same reason as always. Running total: **53 of 54 tests actually pass in this environment**; the 54th file needs `npm install`.

**A quantified correction to the free-tier analysis**: chunked uploads write to D1 far more than the old approach — roughly one write per chunk, so a file near the 1 GB quota (~128 chunks) costs on the order of 130 D1 writes, not the 1–3 the Phase 7/10 analysis assumed. Still comfortable at this project's scale; `docs/Operations.md` now says so with an actual number instead of an estimate that quietly stopped being accurate for large files.

**Unresolved / explicitly out of scope for this pass**:
- Zero-byte file uploads aren't well-supported by this chunking scheme (a 0-length range is malformed under the `Content-Range` grammar used here) — not engineered around, given how rare this is for a coursework tool; fails cleanly (400), doesn't corrupt anything.
- No Cron Trigger for `upload_sessions` cleanup — relies on opportunistic reclaim plus Drive's own ~1-week auto-expiry, to avoid one more piece of deployment configuration. Documented as a known gap in `Operations.md`, not silently accepted.
- Still open, only the project owner can answer: personal Google One vs. Workspace for the 400 GB (see the review findings above).
- All Phase 8–11 gaps remain exactly as documented: no real browser test, `routes.test.js` unexecuted, nothing deployed.

## Sub-folders (added after Phase 12): upload a whole folder without zipping
- **Decision**: sub-folders are *virtual* -- a `path` column on `files` and `upload_sessions` (e.g. `calendar/css`), nothing created per sub-folder on Drive. Chosen over real nested Drive folders / a `parent_folder_id` tree because it needs no extra Drive calls (free-plan Worker limit: 50 outgoing requests per invocation), no new auth model (a sub-folder inherits its student folder's password/token), and deleting/listing stays plain SQL. Trade-off: empty folders can't exist, and Drive itself shows a flat list.
- Backend: `validateDirPath` (validate.js), `path` through upload initiate -> completion -> listing, `DELETE /api/folders/:id/paths` (batched, 10 files per call), migration `migrations/001_add_file_paths.sql` (+ `db:migrate-paths:*` scripts), upload rate limit 60 -> 600/hour/IP.
- Website: `js/paths.js` (pure helpers, tested in `backend/test/paths.test.js`), path bar + folder rows, drag-and-drop of whole folders (`webkitGetAsEntry`), a "choose a folder" picker, 3 files uploaded at a time with one overall progress bar, per-drop cap of 500 files, `node_modules`/`.git`/system files skipped, routes `#/folder/:id/p/<encoded path>`.
- Also fixed in the same pass (found while testing): `escapeHtml` now escapes quotes (a crafted file name could inject an attribute into the file list -- stored XSS in public folders); the right-hand panel now scrolls (it was clipped at one screen height); the `hidden` attribute is no longer overridden by component `display` rules; the CORS list now allows `PUT` (chunk uploads were blocked from the browser); the client recognises the completing upload reply by `id`; two pre-existing tests used a 2-character password the API rightly rejects.
- Verified: 119 backend/unit tests; the real `index.html` + `app.js` driven in jsdom against the real backend (drop a nested folder, navigate, upload inside a sub-folder, hostile names, non-owner view, delete). **Not** verified in a real browser: visual layout, and the browser's own folder-drop behaviour beyond the entry API's documented shape.

## Manager password + recovery questions (added after the sub-folders work)
- **Why**: copying and saving a long management token was too much to ask of every student, and losing it meant losing the folder forever. Google sign-in was considered and declined by the owner (also blocked for now: the OAuth app is stuck in Testing mode, 100-user cap).
- **Design**: owner picks a manager password + 2 recovery questions (8 presets or their own) when creating a folder; the creator is signed in automatically; other devices sign in with the password; "forgot password" = answer both questions and set a new one. Backend: `src/manager.js`, `session.js` (manager sessions `mgr.…` with a `manager_version`, `keyedHash`), `auth.js` (`managementProof`/`assertManagementAccess`: accepts `Manage` sessions AND the older `Bearer` token), routes `POST /:id/manage/login|reset|password`, `GET /:id/manage/recovery-questions`, migration `002_add_manager_password.sql`. Old token-managed folders keep working untouched (`managerMode: "token"`).
- **Deliberate deviation**: the password and answers are HMAC keyed hashes, not PBKDF2 -- creating a folder hashes two secrets in one request and a single PBKDF2 already uses ~5.5 ms of the free plan's ~10 ms CPU budget. Consequence: `UNLOCK_SESSION_SECRET` must never be rotated after launch.
- **Safety net**: 5 sign-in tries / 15 min / IP; recovery 5 tries / hour / IP and 20 / day / folder; a reset or change signs out all other sessions; new password may not equal the viewing password; recovery answers are validated (min 3 letters) and compared normalized.
- Website: create form has the new fields; a visitor sees "I'm the owner -- manage this folder"; owners get Change password + Sign out (instead of Rotate token); an ended session quietly signs the browser out (`session_expired`). No token-copy screen for new folders.
- Verified: 149 backend/unit tests; the real page + real backend in jsdom across several simulated browsers (create, wrong/right password, forgot flow, change password, older sessions ended, sign-out, older token folder unchanged); migrations 001+002 on a real local D1 with an old-style folder. **Not** verified in a real browser (visual layout of the new form fields).
